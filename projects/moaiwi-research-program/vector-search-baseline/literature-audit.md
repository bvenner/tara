## Layer (a) — the evidence anchors: KVerus + LeetProof

### KVerus — see `kverus-deep-read.md`

Full read done. Headline for this note: KVerus's knowledge base is **already hybrid** (deterministic structural extraction + vector semantic index + classifier-routed, version-aligned docs); its ablation says *which knowledge pays where* (structure at repository scale, docs at local scale); its maintenance evidence (toolchain evolution, proof-as-maintenance) is the strongest revision-heavy data in the anchor set.

### LeetProof — certified program synthesis with a multi-modal verifier

**Source.** Feng, Kafle, Gladshtein, Kurin, Pîrlea, Zhao, Müller, Sergey (NUS + ETH Zürich), *Certified Program Synthesis with a Multi-Modal Verifier*, arXiv:2604.16584v1 (17 Apr 2026; ASE 2026). LeetProof = agentic pipeline on **Velvet** (a Hoare-style verifier for imperative programs embedded in Lean, via the Loom framework — a *foundational* multi-modal verifier: dynamic testing + SMT automation + interactive proof scripting in one framework).

**What it does.** Vericoding: NL task description → program + formal specification + machine-checkable proof of alignment, in **validated stages** (specification synthesis → program/invariant synthesis → proof synthesis with residual obligations delegated to frontier AI provers, e.g. Aristotle, with Mathlib search).

**Findings that matter for the Audit:**

1. **The NL→formal projection is where errors concentrate.** Specs synthesized from natural language are "too weak to be meaningful or too strong to be implementable"; the authors found **~10% of the reference specifications in two state-of-the-art benchmarks (VERINA, CLEVER) defective** — under-constraining or misstating intent. A faulty specification dooms even a correct program. *This is the elicitation→formalization loss on the spine (T15's projection loss as currency), empirically measured in the one domain where it can be.*
2. **Validation of the projection exists and is cheap.** Randomized **property-based testing of specifications before any code synthesis** (Plausible): three generated checks per test case — input admissibility; intended I/O satisfies the postcondition; **uniqueness** (no alternative output satisfies it — catches under-specification, e.g. a vacuous implication admitting an always-false implementation). PBT beat the alternatives on cost by a wide margin: symbolic spec testing (SMT-proving tests, Lahiri-style) was "prohibitively expensive" in Lean; loops over interactive proof attempts cost far more "for the same filtering effect." Spec PBT achieved 97.4% semantic accuracy on VERINA. *The missing piece of any elicitation pipeline: generate tests from the informal intent and check the formalization against them. Tests double as human-readable documentation of the formal spec.*
3. **Multi-modal = staged cost allocation.** The pipeline chooses the cheapest sufficient mode per stage: PBT as fast oracle (filter early), SMT for routine obligations, interactive/AI provers only for last-mile residuals. Multi-modal staged pipeline beat single-mode at the same fixed budget, consistently across two frontier LLM backends. *The T14 harness pattern with a cost schedule.*
4. **Guarantees are graded and honest.** PBT can refute but not prove; the stage output is "high-confidence" artifacts; the final certificate comes only from the foundational checker. Revision loops (LLM judge + failure feedback) run inside each stage.

**Mirror image of KVerus on the spine.** KVerus = the *extraction* end (formal sources in; retrieval and reuse out). LeetProof = the *elicitation* end (informal intent in; validated formalization out). Together: **both anchors agree that the specification/formalization layer is the failure concentration** — KVerus's boundary cases (incorrect specs, human repair), LeetProof's ~10% defective reference specs. Any KR decision for a general (non-formal) domain is largely a decision about how to fund and validate that layer.

## Layer (b) — hybrid-search engineering + buy-side prior art (done, scan depth)

### The evaluation literature says: complementarity, not dominance

- **RAG vs GraphRAG systematic evaluation** (arXiv:2502.11371v3, updated 2026-03): RAG better on single-hop/detail/factual queries; GraphRAG better on multi-hop/reasoning; community-based global search sacrifices query-specific detail. **Evaluation-protocol warning:** LLM-as-judge summarization scores are highly sensitive to candidate presentation order (position effects) — directly relevant to criteria v2 design for the three-arm trial. GraphRAG "is not free": higher construction cost, retrieval latency, storage; sensitive to graph-construction quality. Their hybrid strategies (query-type **Selection/routing**; **Integration**/union evidence) give consistent improvements.
- **GraphRAG-Bench** (arXiv:2506.05690, ICLR 2026): GraphRAG **13.4% lower** than plain RAG on Natural Questions and **16.6% lower** on time-sensitive queries; only +4.5% on HotpotQA multi-hop at 2.3× latency. On complex reasoning HippoRAG2 53.38 vs basic RAG 42.93; evidence recall much wider (87.9–90.9% vs 64.5%).
- **QA-GraphRAG** (VLDB/PVLDB 19): graph frameworks don't consistently beat vector on "Local" queries; vector wins local, graph wins global; a **query-adaptive router** over knowledge hierarchy levels fixes it. Notably, naive **1-hop relation integration can beat sophisticated GraphRAG**.
- **"Is GraphRAG Needed?"** (arXiv:2606.25656): pure graph search without semantic info performs poorly (Hit@1 0.14); a **computed (LLM-extracted) KG can actively hurt** vs no graph; predefined (curated) KGs + semantics is where the gains live; again 1-hop integration > complex GraphRAG.
- **Cyber-threat-intelligence eval** (arXiv:2604.11419): hybrid graph–text up to +35% on multi-hop vs vector; graph-only failure modes = latency variance and **overconfident answers when information is missing**; query-repair/hybrid most reliable.
- **Domain benchmarks** (ORAN, arXiv:2507.03608; ontology-KG study, arXiv:2511.05991): hybrid best factual correctness; **attaching text chunks to graph nodes** consistently improves grounding (ontology-KG+chunks 90% vs 15% for text-ontology without chunks, 60% vector baseline).

### The production retrospectives (the balanced view)

- **"We Piloted a Graph and Killed It"** (gabezen.com, 2026-08): extraction is **non-deterministic** — same corpus re-extracted: 147 vs 139 nodes, only **15.85% of node labels matched** ("a human reads those as the same thing; a join key does not"); incremental update broken (edit never re-extracted; graph ballooned 157→542 nodes); tool tracker showed ~30% junk stub nodes, up to 62% duplication bloat. NO-GO with written revisit conditions: incremental-update fixes; **entity merging / stable labels**; or three real queries a month search demonstrably can't answer.
- **"Why your knowledge graph isn't helping your RAG"** (alir.me): the **re-ranker trap** — their fusion layer only gave graph credit to passages vector search had already retrieved, making the graph's unique capability (surfacing vocabulary-disjoint bridge passages) impossible *by construction*: "we had measured the bug and called it the concept." Diagnostic: **count passages that arrived from the graph alone** (theirs had always been zero). After repair, bridge-question recall ~doubled but the scoreboard still tied — densest facts lived in tables (invisible to prose extraction) and the hardest questions were aggregations (**JOINs, not walks**). Question distribution decides.
- **13k-notes Neo4j pilot** (tonytonggg.com, 2026-10): graph alone retrieved **worse** than existing hybrid search (0.39 vs 0.53 gold-in-top-10); layered on top: **tie overall**; helped temporal questions (0.44→0.53 gold-in-budget), **hurt "plans that never happened" questions** (0.70→0.63 — graph lines displace chunks holding the gold note); 4–9 s vs 0.8 s latency, most of it the relevance trim. Routing rule: hybrid default; graph earns its seconds only for answers assembled across dates/entities or depending on **whether a statement is still true**.
- **"The Graph We Finally Built"** (it-blue.one, 2025-10): vector 70% / graph 64% / hybrid 88% on their labelled set; **~1 in 8 extracted relations wrong** (asserting dependencies the text only implied conditionally) — 4 of 6 weeks went into extraction validation to get under 3%; **"build the validation before the graph"**; human corrections kept as **a separate layer that survives rebuilds** ("the piece we would tell anyone else to build first"). Threshold rule: count questions needing a chain; below ~1/5, a join/summary layer is cheaper.
- **"GraphRAG Two Years Later"** (zhguichen.github.io, 2026-08): still maintained, never the default upgrade; the production consensus is **hybrid routing** (simple→vector, complex→agentic, relational→graph); Atlan's rule: <1000 entities with simple relations → vector at ~1/10 the cost.
- **Small-scale production drop** (kingsleyonoh.com, 2026-03): optional graph layer (zeros tolerated); at <1000 docs removing Neo4j moved relevance 0.83→0.81; the graph earns its place at ~50k docs as a tiebreaker.
- **"Pilots succeed, production fails quietly"** (mohammadkhan.dev, 2026-04): triple-index synchronization (text/vector/graph) is the hidden data-engineering cost; **graph decay 15–20% from ground truth per quarter** without automated refresh; community summaries never auto-update; if <10% of queries are multi-hop the investment isn't justified; start narrow (contracts, compliance, specs).
- **salmanzafar.dev (2025-09):** extraction quality is the ceiling (a missed relation is an edge that doesn't exist — silent zeros); graph refresh ~an order of magnitude more compute than index refresh; community summaries = serious per-corpus LLM spend; **80%+ of production traffic is lookup-shaped** — route by question.

### Maintenance / incremental-update engineering (the revision discipline appears in production)

2026 tooling converges on one recipe, strikingly close to our D3 revision discipline + L37 fixity findings:

- **Primitives** (FalkorDB, 2026-10): content hash/version fingerprint per source + **source provenance on every node/edge** → then diff-based reconciliation, idempotent writes, and **retraction of stale data**. Full-rebuild vs append-only vs true-incremental table; append-only "accumulates stale and contradictory data."
- **Supersession as a first-class move** (cognilium.ai, 2026-06): "**supersede, do not just add** — the old fact is not necessarily deleted, but it stops being the answer the graph returns"; scoped revalidation proportional to the change, not the graph. *This is add/retract/supersede arriving as production practice.*
- **Document-lifecycle subgraphs** (Jigsaw-LightRAG, 2026-02; CocoIndex): per-document subgraphs + memoized extraction by content hash → incremental LLM cost proportional to change, token-free global dedup, **stable graph structure across repeated runs** (directly answering the GABE non-determinism complaint); deletions clean up automatically; prompt/model changes invalidate memos and re-extract.
- **Cost algebra + hub-entity dirt** (Graph RAG from Scratch, ch.27): extraction proportional to change is easy; summaries/reports are the trap because hub entities appear in most new documents; keep raw extraction outputs cached — "the graph becomes a function of the cache"; temporal edges ("who was CTO then") for history.
- **Confidence-decay updates** (adaptiverecall.com): new extractions start moderate confidence, accumulate across sources, deleted triples decay rather than vanish; scheduled full validation cycles catch drift.

### Decision-relevant takeaways (qualitative)

1. **Query distribution is the deciding variable** — everywhere. Routing (simple→vector, relational/aggregate→graph) is the production consensus; published thresholds all say the same thing (multi-hop share below ~10–20% → graph not justified yet).
2. **Construction quality is the ceiling, and LLM-extracted prose graphs are shaky** — non-determinism, duplication, 1-in-8 bad edges, computed-KG-underperforms findings. **Extraction from formal sources (KVerus's code-metadata route) sits far above LLM prose extraction** on this axis — the strongest argument for the extraction end of the spine wherever formal sources exist (Fortress/Rust).
3. **Maintenance is the real cost, but the recipe now exists**: content hashes + per-element provenance + diff reconciliation + **supersession semantics** + corrections-survive-rebuilds + scoped revalidation. This *is* our revision discipline (D3) + L37's fixity/attitude layer, independently arrived at. Adopting it is cheaper than inventing it.
4. **Wiring traps are silent** (the re-ranker trap; graph-only overconfidence; budget crowding): any hybrid must measure "what arrived from the graph alone" and protect chunks from budget displacement.
5. **The skeptical default survives**: "the reason RAG sometimes fails is naive retrieval, not vector search itself, and naive retrieval is cheap to fix relative to standing up a graph" — consistent with D7; fancier machinery must beat a *well-built* baseline, not a strawman.
6. **Evaluation fragility** (judge position effects; query-distribution sensitivity) → criteria v2 must fix query mix and presentation order, and prefer retrieval-level measures (gold-in-budget, graph-alone contribution) over judge scores.

## Layer (c) — candidate explicit-KR systems (done)

- **RDF 1.2 triple terms** (W3C Candidate Recommendation, 2026-04-07): a reified triple can appear as a **triple term, an asserted triple, or both** — "your graph can record that a source claims something **without the graph itself claiming it is true**." *This is the claim-vs-assertion (attitude/attribution) primitive L37 found missing in-house, now a standard* — and property graphs have "no direct equivalent." Cost side: RDF is hard for LLM retrieval (CypherBench, ACL 2025: Wikidata's 4M entity types / 12K relation types blow past context windows; identifiers, unnormalized literals) — the practical fix is **property-graph views over RDF**.
- **Property graphs (LPG/Neo4j-class):** tooling maturity, schema flexibility, native traversal, **native vector integration** (Neo4j vector indexes = hybrid graph+vector in one store); agent-friendly via **typed tool contracts** (bounded traversal, trust tiers, schema validation — not raw Cypher). Claims/reification possible but clunky. ISO GQL now standard.
- **Hypergraphs:** n-ary relations native (matches TARA's hyperedges and the multi-succedent program's translation targets); **weak tooling** — no mature hypergraph DB at Neo4j scale, no standard query language (TARA's `graph_query.py` is the usual custom-API case); most stores serialize hyperedges as binary internally. Formal machinery (string diagrams/DPO — desk pass) is the strength; production machinery is the gap.
- **Hyper-relational KGs** (qualifiers on triples: (h,r,t,{q:v}) carrying time/source/condition) are now the standard research object (SIGMOD/VLDB 2025+), with KGs repositioned as the **verifiable grounding layer for LLMs** — the pragmatic middle between triples and hypergraphs.
- **Ologs/FDM** (desk pass): KR↔DB translation with loss-bearing migration functors — the theoretical home for the translation criterion; T17's territory.
- **Production KG patterns** (woyce.ai; arunbaby.com): the winning split is RAG for prose + KG for **deterministic constraints** (ownership, dependencies, policy); construction pipeline = extract → **entity resolution** → validate (human review for high stakes) → merge **versioned/auditable**. Extraction errors "structural": a missed relation is an edge that doesn't exist.

**Audit takeaway.** The claim/attitude/revision layer we want is: standardized in RDF 1.2 (but retrieval-hostile), absent from LPG (but LPG is agent- and vector-friendly), native-but-immature in hypergraphs (but formalized best — the multi-succedent program). No off-the-shelf system ships our combination; **the differentiator is buildable in an LPG or hyper-relational store with provenance**, and it is exactly the piece T17/the translation program would formalize. ## Layer (d) — proof-engineering / human-LLM-agent collaboration evidence (done)

- **Rango** (ICSE 2025 distinguished paper; arXiv:2412.14063): retrieval-augmented proving for Coq — retrieves **worked proofs and lemma statements from the current project at every proof step**, adapting to the evolving proof state. Headline splits: **proof retrieval +47%** theorems proven vs **lemma retrieval +3%** — *retrieving worked examples beats retrieving premises*. And **Rango-PRE** (plain prefix context) nearly matches full retrieval when the needed context is near; Rango-Hybrid (alternate the two) wins overall. *Routing again — and "local context as originally written" has real value (echoes the chunk-integration and budget-crowding findings of layer b).*
- **Oversight burden is the hidden cost** (arXiv:2606.05770): the cumulative effort to review/validate/repair/integrate AI artifacts emerged as *the* most-discussed hidden cost of AI in SE.
- **Human-AI agentic code review at scale** (arXiv:2603.15911; 278,790 review conversations, 300 OSS projects): AI review comments are longer and 95% defect-focused; humans uniquely add understanding, testing, **knowledge transfer**; **AI suggestions adopted 16.6% vs human 56.5%**; over half of unadopted AI suggestions wrong or otherwise fixed; adopted AI suggestions raise complexity/size more; conversations ending on the AI's word are rejected far more (15.6% vs 7.8%) → **a human should have the last word before merge**.
- **Trust calibration, not diffing** (JetBrains participatory study, arXiv:2606.01969): reviewing LLM multi-file changes is a trust-calibration problem; the three-level workflow (overview → file → snippet) with risk-per-line/file signals is what reduces review effort.
- **Oversight work in practice** (17 developers, ACM 3812402): four forms — **a priori control, co-planning, real-time monitoring, post hoc review** (preventative and proactive, not just reactive); pain points: cognitive distance from agent-written code, re-review every iteration; heuristic: tests as guarantees. **"On Autopilot?"** (arXiv:2601.13754): AI-co-authored PRs merge faster with ~80% receiving *no* explicit review; 86.9% of projects lack AI guidelines — the oversight gap is real.
- **Field experiment** (ESEM 2025): review-context assembly via a RAG pipeline helped; hybrid proactive/on-demand design best balances efficiency, trust, reviewer control. Eye-tracking (ACM 3744916): half of AI suggestions never looked at; each costs a flow-breaking micro-interruption.

**Audit takeaway (T14's fixed lens has an empirical base now).** The harness requirements are evidenced, not just asserted: context assembly must serve *review* (the dominant cost); human judgment must remain the last, confirmatory step; risk/confidence signals must be exposed at attention granularity; worked examples are the highest-value retrieval unit (Rango) — which is an argument for experience/claim records over bare premise stores.
