TARA is faced with a chicken-or-egg problem, in that it is intended to be a research assistant to help develop multi-agent systems (with a greatest fixed point a planetary-scale cyber-physical-social systems), but is also itself a multi-agent system. This means that it also has a system development component, which requires choices about logic, programming languages, explicit and implicit knowledge representation, etc. My intuition is that this is a feature, not a bug, but does force continuously rebuilding the system development component as the research assistant learns more about multi-agent systems. This is a classic "bootstrapping" problem (or better yet, the German version that requires pulling up by ones hair).

The current stack for TARA uses Python as a programming language and Pydantic AI as an agent-based system. It has a theory of multi-agents systems based in the temporal logic of actions, formalized in Roqc and implemented in the *plumbing* specification language. Using these components, it specifies a research agent flow that investigates the literature, downloads publically-accessible PDF files, and converts the PDF to text. It uses a python-based hypergraph library to convert the extracted text to a hypergraph knowledge representation. I am currently working on moving the agent specification to the plumbing language, which gives an agent-based workflow orchestration layer with typed JSON boundaries. There is a fair amount of overlap between plumbing and the Pydantic AI stack and the question is whether a ".plumb" file can serve as the architecture for the research assistant itself. If this architecture can be specified at a high level, it may be possible to reflect and improve the research agent architecture using evidence from specific runs.  

It's interesting to compare my current agent workflow to the (LeetProof system}[https://arxiv.org/pdf/2604.16584]. This is a very nice multi-agent system implementation of a "certified program synthesis" workflow for imperative programs. The synthesis is performed by Lean and Velvet; the latter is a Dafny-style verifier for imperative programs. The overall workflow is to convert natural-language based specifications into properties specified in Lean. The approach is "multi-modal" in that the specification is transformed into a certified program in a number of stages, and that different approaches including property-based testing and tactic-based proofs, are used to generate the transformation. 

What is interesting is that the agent workflow is implemented in Python and is not itself formalized. This raises a natural question - could a system like plumbing be implemented in Lean in order to formalize the agent workflow? Or could plumbing itself be used to formalize the workflow prior to reimplementing it in Lean? The LeetProof system is divided into three major sections - generating Hoare-style specifications from natural language requirements, developing a Velvet program to meet this requirements, and developing loop invariants from the Velvet program. Although there are loops within each stage, the overall process is very "waterfall". 

Another idea is to extend the tool to include Gleason's notion of program refinement. A certified program is refined by finding a different program with higher performance that is bisimilar to the certified program. Gleason's claim is that bisimulation perserves this certified property. The additional requirements for refinement could be considered "non-functional" (e.g. Quality attributes, constraints, or performance standards (e.g., security, speed, reliability, or compliance)).

There is also the question of whether something the LeetProof system could be included in a broader research flow. By starting with pretty rigorous natural language specifications, the tool neglects the less glamorous work of developing good natural language specifications. This process is called "requirements engineering" in the systems engineering literature. 

Another question is whether the hypergraph knowledge representation is the right approach for an explicit knowledge tool. I haven't really demonstrated that either the hypergraph tool improves any process, whether this is a good approach to context engineering, or how it compares to other knowledge representation formalisms.

The "ret-tssi-value-dynamics" research proposal that was developed using only LLM calls is still my most interesting and detailed work. There are a number of research questions that were raised in this development that could potentially be formalized with a vericoding-type system. While I'm still not sure of the impact of quality of this research proposal, it does seem simple enough to investigate. It also ends with development of an agent-based model, so it does fit into my larger track of research.
